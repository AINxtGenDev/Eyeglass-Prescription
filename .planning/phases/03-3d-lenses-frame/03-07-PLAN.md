   - `createFrame(scene)`: meshes for rimOD and rimOS (each in its own Group positioned with `boxingCentreX(eye, A, DBL)`), bridge, templeOD, templeOS, hingeOD, hingeOS. Geometries are created once from `allocFrameBuffers()` with the static index arrays, plus a frame buffer pool.

   - A frame item with ok false hides the frame meshes, keeps the lenses, and explicitly leaves each lens group's `position.z` at the last valid lensZ (lens-critic round 2 MINOR 7). frame.js keeps `lastLensZ` (initially `{ OD: 0, OS: 0 }`), updates it only from ok items, and applies it on every frame attach. Reason, written as a comment: keeping the value means the lenses do not jump while the frame is missing; with the rims hidden no lens/rim disagreement can be seen; the next ok frame item sets the common plane again. Resetting to 0 would move anisometropic lenses for a state that has no rim to align with.
3. `src/ui/view/view.js`:
   - `update(inputs)` adds the frame item `{ slot: 'frame', frame: { shape, A, B, DBL }, eyes: { OD: ok ? surfaces : null, OS: … }, rimDepthMm, templeMm, buffers: framePool.take() }` whenever the frame inputs are valid, so the frame shows even with no computable eye.
   - Per-item keys (lens-critic round 2 MINOR 7): each slot has its own key. A lens item's key covers the eye, every surfaces field, the shape, A and B. The frame item's key covers the shape, A, B, DBL, both eyes' surfaces (or null), rimDepthMm and templeMm. update() sends only the items whose key differs from the key of the item last attached in that slot from a current reply. It compares with the attached key, not the last sent key, so the items of a dropped queued job or of a stale reply are sent again with the next job. A rim-depth or temple change therefore sends only the frame item. An Rx change of one eye sends that lens and the frame (the rim follows the bevel curve), not the other lens. Unchanged slots keep their attached geometry and buffers; pooled buffers are taken only for items that are sent.
   - When no item changed but the view still has a mesh job outstanding (a requestMesh gen without its reply yet), call `requestMesh([])`. The outdated job is then dropped (its buffers come back as `dropped`) or its reply arrives as current: false. Without this, a quick −2 → −3 → −2 would attach the −3 mesh.
