  - The latency is "from the time the user begins the interaction to the moment the browser is next able to paint a frame".
  - The thresholds apply to "the 75th percentile of page loads recorded in the field". This plan applies 200 ms to **every** measured edit, which is stricter.
- **Event Timing**, https://developer.mozilla.org/en-US/docs/Web/API/PerformanceEventTiming:
  - `observer.observe({ type: "event", durationThreshold: 16, buffered: true })`;

  - "Baseline 2025 Newly available".

  - the recommended form is `new Worker(new URL('./worker.js', import.meta.url), { type: 'module' })`;
  - "The worker detection will only work if the `new URL()` constructor is used directly inside the `new Worker()` declaration";
  - "all options parameters must be static values (i.e. string literals)".

  - MDN worker-src: "If this directive is absent, the user agent will first look for the child-src directive, then the script-src directive, then finally for the default-src directive, when governing worker execution". ## Design decisions (planner; Claude's discretion where the user did not decide)

- **Protocol** (pure, `src/state/compute-protocol.js`, node-testable).
  - Main → worker:
    - `{ type: 'compute', id, eyes: { OD?: { seq, spec }, OS?: { seq, spec } } }`;
    - `{ type: 'bench', id, caseId }`, where caseId ∈ `normal | frameMiss | grenzfall | rescan`. The cases are resolved inside the worker from bench-cases.js, and the frame-miss counter lives in the handler closure.
  - Worker → main:
    - `{ type: 'ready' }` on start;
    - `{ type: 'result', id, eyes: { OD?: { seq, result }, … }, computeMs }`;
    - `{ type: 'bench', id, caseId, median, tail, runs, ok }`;
    - `{ type: 'error', id, eyes: [...], message }`.
  - The handler wraps everything in try/catch and never throws.
- **Latest-wins without cancellation.**
  - At most one job is in flight. Newer requests overwrite one pending slot per eye.
  - A response is applied per eye only if its `seq` equals that eye's latest wanted seq, otherwise it is dropped.
  - The worker is **not** terminated on supersede. Restarting would reload the module and lose JIT warm-up. The extra wait is bounded by one in-flight job, at most the rescan pair (178 ms at 4×). The SUMMARY states this.
  - Compute jobs are dispatched before queued bench jobs, but a running bench job is not interrupted.
- **Transfer.** No transferables are used. LensResult contains only plain objects, numbers, strings, booleans and null: no typed arrays (the outline is not part of the result; checked in src/engine/evaluate.js and metrics.js). The specs are small. A structuredClone round-trip unit test proves it.
- **Per-eye memo on the main side.** Inside the client, an eye whose `JSON.stringify(spec)` equals the key of its last wanted request is not re-sent. An eye whose key equals the last received result's key is answered from the cache with no worker round trip (this matches the 01-14 memo). `src/state/memo.js` then has no importer. Delete it and its test (an orphan created by this change), after `grep -rn "memoLast" src test e2e` shows only memo.js and memo.test.js.
- **Busy rule.**
  - `BUSY_AFTER_MS = 50` (RAIL).
  - The timer starts at the earliest open input's timeStamp (`delay = max(0, 50 − (now − openTs))`). If the latest results are not delivered by then, `onBusy(true, eyes)` is called. `onBusy(false)` is called when all wanted eyes are current.
  - Normal cases (≈ 6–7 ms per eye in the worker at 4×) never flash the indicator.
- **Busy UI** (light DOM, text first, not colour-only):
  - `#result` gets `aria-busy="true"`;
  - the eye's Hinweis cell shows `t('result.computing')` = 'rechnet …';
  - the eye's value cells get `data-stale="true"` (CSS: italic plus a dotted underline; no opacity change, so contrast and axe color-contrast are unaffected);
  - `#calc-status`, a plain `<p>` that is not a live region, shows `t('result.computingNote')`.
  - When busy ends, everything is cleared and the Hinweis cell is restored by the normal render.
- **Error and fallback.**
  - Worker construction throws, or an `error` event arrives before `ready`: the client switches to the synchronous transport (same handler, called directly; the response is delivered via `queueMicrotask`). In-flight and pending jobs are re-sent. `#compute-mode` shows `t('tech.mode.sync')` with `data-mode="sync"`.
  - An `error` response, or an `error`/`messageerror` event after `ready`: the in-flight eyes render dashes with the status `t('compute.failed.title')` and a paragraph `t('compute.failed.explain')` in the diag box. The busy state is cleared and pending work continues. The English message goes to `console.warn` only.
- **Timing** (main-thread, for the restated ENG-09). The method for "after paint" is unchanged from 01-14 (rAF + setTimeout, Nolan Lawson 2018).
  - Ring `frameTask`: the frame-callback duration (frameStart → end of update(), including postMessage).
  - Ring `reaction`: input timeStamp → after paint of that frame.
  - Ring `resultTask`: the duration of the result-render handler.
  - Ring `result`: earliest open input timeStamp → after paint of the render that made all eyes current.
  - Ring `compute`: `computeMs` from the worker.
  - Each ring holds the last 10 values. The readouts show median and the longest value.
  - Event Timing cross-check: the longest `duration` of the last 10 `event` entries with `interactionId > 0`, feature-detected via `PerformanceObserver.supportedEntryTypes`. It is informational; when unsupported the readout says 'nicht verfügbar'.
- **Lint.** Add a flat-config block for `src/worker/**/*.js` with `globals.worker` (checked: `globals` 17.14.0 has a `worker` key with `self` and `postMessage`) and no-restricted-imports for three and `**/ui/**`.
